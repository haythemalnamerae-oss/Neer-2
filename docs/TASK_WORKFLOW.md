# دورة المهام — Neer-2

**التاريخ:** 2026-11-12  
**الفرع:** main  
**الحالة:** توثيق مطابق للمصدر الحالي؛ التنفيذ التشغيلي الكامل غير معتمد بعد.

## المسار الموجود حاليًا

1. تنشئ الواجهة المهمة عبر `NewTaskModal`.
2. ترسل `createTaskBundle` الحزمة إلى `POST /api/v1/tasks/create-bundle`.
3. يتحقق API من جلسة Supabase وعضوية المؤسسة وصلاحية `tasks.create`.
4. تنفذ `create_task_bundle` معاملة واحدة لحفظ المهمة والمكلفين وقائمة الفحص والخطوات وسجل الإنشاء والتدقيق والإشعارات.
5. تسجل نتيجة المهمة عبر `record_task_outcome_bundle`؛ وتدخل المهمة المكتملة حالة `pending_approval`.
6. يراجع صاحب صلاحية `tasks.approve` المهمة عبر `review_task_approval`.
7. تحفظ الخطوات والمهام الفرعية والتعليقات والتقارير اليومية والمرفقات في جداولها المرتبطة بالمهمة مع RLS.

## الكيانات القائمة

`tasks`, `task_assignees`, `task_checklist_items`, `task_steps`, `task_subtasks`, `task_daily_updates`, `task_history`, `task_attachments`, `task_comments`, `task_events`, `follow_ups`.

لا يوجد جدول مستقل لأنواع المهام أو سجل موافقات normalized. حقل `task_type` نصي، وحالة الموافقة ممثلة حاليًا ضمن `tasks.status` وحقول outcome/approval.

## حدود معروفة تمنع اعتماد المرحلة

- الموافقة والتنفيذ غير مفصولين إلى عمودين مستقلين؛ `status` الحالي يمثل حالات من المسارين.
- لا توجد سياسة إعدادات مستقلة تسمح بالبدء قبل الموافقة.
- المهمة الفرعية مرتبطة بصف في `task_subtasks`، لكن تفاصيلها لا تطابق بطاقة مهمة كاملة مستقلة بكل الحقول.
- الخطوات لا تملك حاليًا مسؤولًا مستقلًا أو اعتمادًا على خطوة سابقة أو طلب موافقة مستقلًا.
- إنشاء نوع مهمة جديد يُدار في الواجهة كقيمة نصية، وليس ككيان مركزي له صلاحيات وتعطيل.
- لا توجد اختبارات E2E موثقة لتدفق كامل باستخدام مستخدمين متعددين.

## ضمانات المصدر الحالي

- المؤسسة مشتقة من عضوية الجلسة على الخادم.
- إنشاء المهمة حزمة ذرية.
- أحداث GPS لها سجل مستقل وقيود إحداثيات وidempotency.
- إلغاء المهمة يتم عبر workflow ولا يحذف الصف.
- سجلات الأحداث/التاريخ تخضع لقيود قاعدة البيانات وRLS؛ يجب عدم اعتبار CRUD المحلي أو demo data مصدر حقيقة.
