## ما نُفذ في هذه الجولة

1. **طلب المهمة والاعتماد:** إضافة `task_requests` ومساري إنشاء الطلب ومراجعته وإعادة إرساله بعد طلب التعديل. اعتماد الطلب يحوله إلى بطاقة مهمة فعلية، ويمنع المنشئ من مراجعة طلبه.
2. **فصل الاعتماد عن التنفيذ:** إضافة `approval_status` و`execution_status` للمهام، مع مشغل يمنع تغيير حالات الاعتماد/التنفيذ الحساسة خارج مسارات RPC المعتمدة.
3. **دليل أنواع المهام:** إنشاء `task_types` مع 8 أنواع أولية لكل مؤسسة، ربط واجهة إنشاء المهمة بالدليل، وربط المهام المباشرة بمفتاح النوع.
4. **المهام الفرعية المستقلة:** اعتماد المهمة الفرعية ينشئ بطاقة مستقلة في `tasks` مرتبطة بالمهمة الأم، وتظهر في قائمة المهام. إكمال البطاقة يحولها إلى `pending_approval`، واعتماد النتيجة يحدث بطاقة الابن وسجل المهمة الفرعية معًا.
5. **الخطوات:** إضافة مسؤول للخطوة، واعتمادية بين الخطوات، وخيار اعتماد بعد الإنجاز. إضافة حارس SQL يمنع دورات الاعتماد، ومنع الموظف الميداني من إعادة تهيئة مالك الخطوة أو اعتمادياتها.
6. **المستخدمون:** إضافة واجهة دعوة ومورد API ينشئ دعوة Supabase Auth ويربط `app_users` و`organization_members` مع تعويض حذف الحساب عند فشل الربط. يتطلب التشغيل ضبط `SUPABASE_SERVICE_ROLE_KEY` في بيئة الخادم فقط؛ لم يتم التحقق من وجوده في بيئة النشر.
7. **التقارير:** إضافة endpoint لتجميع مؤشرات المهام والمالية وأداء الفريق خادميًا مع جلب صفحات متتابعة (500 سجل/صفحة وحد 50,000). أضيف ملخص خادمي إلى شاشة التقارير؛ بقية الرسوم والتفاصيل القديمة ما زالت تستخدم ReportsService المحلي.
8. **الحماية والتحقق:** منع CRUD المباشر للخطوات والمهام الفرعية على دور authenticated، وحصر الكتابة في RPCs المخصصة. إصلاح سجل تدقيق عناصر المهام (action/entity) وخطأ تركيب نص إشعارات الطلبات بعد كشفهما في اختبار SQL. إضافة أزرار اعتماد/إعادة نتيجة المهمة في TaskDetailsModal، وإخفاء بدء/إنهاء المهمة أثناء انتظار المراجعة؛ يبقى قرار الصلاحية النهائي في RPC.

## الحالة الحية المؤكدة

- 40 ترحيلاً مطبقًا حتى `20261112152539`.
- 30 جدولًا عامًا، وجميعها RLS مفعّل.
- 75 سياسة RLS.
- 8 أنواع مهام في الدليل.
- RPCs الطلب والمراجعة وإعادة الإرسال وإنشاء/تحديث المهام الفرعية وحالات الخطوات موجودة.
- اختبارات SQL داخل معاملات rollback نجحت لإنشاء مهمة وطلب ومهمة فرعية، ومنع اعتماد المنشئ لطلبه، ومنع دورة اعتماد الخطوات، ومنع الكتابة المباشرة، وإنشاء بطاقة ابن ثم إكمالها واعتماد نتيجتها؛ وتم التحقق من عدم بقاء سجلات الاختبار.
- امتيازات INSERT/UPDATE/DELETE المباشرة على `task_steps` و`task_subtasks` غير ممنوحة لـauthenticated.
- كشف فحص الامتيازات أن `TRUNCATE` كان ممنوحًا لدورَي `anon` و`authenticated` على 20 جدولًا عامًا؛ أُزيل الامتياز عن جميع جداول `public`، وأعاد استعلام التحقق صفر جداول ما زالت تمنح TRUNCATE للدورين.
- المهام والطلبات والمهام الفرعية والخطوات ما زالت بلا سجلات أعمال؛ لذلك لم يمكن إثبات تدفقات أعمال موجبة على بيانات تشغيلية.

## ما لم يثبت بعد

- لم يتم تشغيل lint أو TypeScript build أو browser/mobile E2E؛ لا بناء سحابي ولا نشر.
- لم يتم اختبار دورة موظف يرسل طلبًا ومدير آخر يعتمده بحسابين Auth فعليين؛ اختبارات قاعدة البيانات استخدمت معرّف منشئ اصطناعيًا داخل معاملة rollback لاختبار فرع الاعتماد.
- تم اختبار إنشاء البطاقة الفرعية وإكمالها واعتماد نتيجتها داخل قاعدة البيانات بمعاملة rollback؛ لم يتم اختبار ظهورها وتنفيذها من واجهة المتصفح.
- لم يتم اختبار كسر دورة الاعتماد عمليًا عبر جلستين؛ تم التحقق من وجود trigger فقط.
- لم يتم اختبار دعوة مستخدم حقيقية؛ endpoint يتوقف برسالة واضحة إذا لم يكن `SUPABASE_SERVICE_ROLE_KEY` مضبوطًا.
- ملخص التقارير الخادمي أضيف إلى المصدر ولم يختبر عبر جلسات أدوار حقيقية؛ التقارير التفصيلية والرسوم القديمة لم تتحول بالكامل بعد.
- أُعيد فحص Supabase Advisors: لا تحذيرات health؛ تحذير أمني واحد لإعداد حماية كلمات المرور المسرّبة المعطّل، و26 دالة SECURITY DEFINER قابلة للاستدعاء من authenticated (تتطلب مراجعة لكل دالة قبل تغيير grants حتى لا تتعطل الواجهات). فحص الأداء أظهر مفتاحين أجنبيين بلا فهرس و32 فهرسًا لم يظهر استخدامها حتى وقت الفحص؛ لا تُحذف الفهارس اعتمادًا على لقطة استخدام قصيرة.
- أضيف مسار اعتماد النتيجة في واجهة تفاصيل المهمة. لم ينجح اختبار موجب لاعتماد النتيجة عبر جلستين Auth مختلفتين؛ محاولات إعداد مستخدم اختبار اصطدمت بحارس immutable creator، ولم تُجر أي تغييرات دائمة.
- يجب تشغيل `supabase migration list` محليًا ومقارنته بالملفات قبل أي `db push`.

## قرار القبول
