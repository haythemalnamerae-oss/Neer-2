# حالة تنفيذ استكمال النقاط الثماني — Neer-2

**آخر تحديث:** 2026-11-12  
**المستودع:** `haythemalnamerae-oss/Neer-2`  
**الفرع:** `main` فقط  
**Supabase project:** `xtfuvxomfhlfjtpljofh`

## ما نُفذ في هذه الجولة

1. **طلب المهمة والاعتماد:** إضافة `task_requests` ومساري إنشاء الطلب ومراجعته وإعادة إرساله بعد طلب التعديل. اعتماد الطلب يحوله إلى بطاقة مهمة فعلية، ويمنع المنشئ من مراجعة طلبه.
2. **فصل الاعتماد عن التنفيذ:** إضافة `approval_status` و`execution_status` للمهام، مع مشغل يمنع تغيير حالات الاعتماد/التنفيذ الحساسة خارج مسارات RPC المعتمدة.
3. **دليل أنواع المهام:** إنشاء `task_types` مع 8 أنواع أولية لكل مؤسسة، ربط واجهة إنشاء المهمة بالدليل، وربط المهام المباشرة بمفتاح النوع.
4. **المهام الفرعية المستقلة:** اعتماد المهمة الفرعية ينشئ بطاقة مستقلة في `tasks` مرتبطة بالمهمة الأم، وتظهر في قائمة المهام. نتيجة البطاقة تمر بمسار اعتماد المهمة المعتاد.
5. **الخطوات:** إضافة مسؤول للخطوة، واعتمادية بين الخطوات، وخيار اعتماد بعد الإنجاز. إضافة حارس SQL يمنع دورات الاعتماد، ومنع الموظف الميداني من إعادة تهيئة مالك الخطوة أو اعتمادياتها.
6. **المستخدمون:** إضافة واجهة دعوة ومورد API ينشئ دعوة Supabase Auth ويربط `app_users` و`organization_members` مع تعويض حذف الحساب عند فشل الربط. يتطلب التشغيل ضبط `SUPABASE_SERVICE_ROLE_KEY` في بيئة الخادم فقط؛ لم يتم التحقق من وجوده في بيئة النشر.
7. **التقارير:** إضافة endpoint لتجميع مؤشرات المهام والمالية وأداء الفريق خادميًا مع جلب صفحات متتابعة (500 سجل/صفحة وحد 50,000). أضيف ملخص خادمي إلى شاشة التقارير؛ بقية الرسوم والتفاصيل القديمة ما زالت تستخدم ReportsService المحلي.
8. **الحماية والتحقق:** منع CRUD المباشر للخطوات والمهام الفرعية على دور authenticated، وحصر الكتابة في RPCs المخصصة. التحقق من RLS والصلاحيات ووجود الدوال والقيود عبر SQL.

## الحالة الحية المؤكدة

- 35 ترحيلاً مطبقًا حتى `20261112144750`.
- 30 جدولًا عامًا، وجميعها RLS مفعّل.
- 75 سياسة RLS.
- 8 أنواع مهام في الدليل.
- RPCs الطلب والمراجعة وإعادة الإرسال وإنشاء/تحديث المهام الفرعية وحالات الخطوات موجودة.
- امتيازات INSERT/UPDATE المباشرة على `task_steps` و`task_subtasks` غير ممنوحة لـauthenticated.
- المهام والطلبات والمهام الفرعية والخطوات ما زالت بلا سجلات أعمال؛ لذلك لم يمكن إثبات تدفقات أعمال موجبة على بيانات تشغيلية.

## ما لم يثبت بعد

- لم يتم تشغيل lint أو TypeScript build أو browser/mobile E2E؛ لا بناء سحابي ولا نشر.
- لم يتم اختبار دورة موظف يرسل طلبًا ومدير آخر يعتمده بحسابين فعليين.
- لم يتم اختبار إنشاء بطاقة فرعية واعتمادها ثم ظهورها وتنفيذها واعتماد نتيجتها من واجهة المتصفح.
- لم يتم اختبار كسر دورة الاعتماد عمليًا عبر جلستين؛ تم التحقق من وجود trigger فقط.
- لم يتم اختبار دعوة مستخدم حقيقية؛ endpoint يتوقف برسالة واضحة إذا لم يكن `SUPABASE_SERVICE_ROLE_KEY` مضبوطًا.
- ملخص التقارير الخادمي أضيف إلى المصدر ولم يختبر عبر جلسات أدوار حقيقية؛ التقارير التفصيلية والرسوم القديمة لم تتحول بالكامل بعد.
- يجب تشغيل `supabase migration list` محليًا ومقارنته بالملفات قبل أي `db push`.

## قرار القبول

**التنفيذ البرمجي والقاعدي للنقاط الثماني تقدم بشكل ملموس، لكنه ليس اعتمادًا تشغيليًا بنسبة 100%.** لا أصفه بالمكتمل حتى تنجح اختبارات البناء والمتصفح والأدوار الحقيقية، ويُضبط سر دعوات Auth في بيئة الخادم، ويُختبر ملخص التقارير من حسابات مختلفة.
